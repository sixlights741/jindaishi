## 三、问题清单（按严重度）

### P0-1 「云端失败降级为本地规则」被改成了一句玩笑话 ⚠️ 最严重

`src/server.js:612-617`：

```js
return res.json({
  answer: "今天晚上吃青椒肉丝盖饭!",
  source: "fallback-fixed",
  model: "fixed-fallback",
  fallbackReason: cloudAttempt.fallbackReason,
});
```

**实测**（本地，AI Key 是失效的）：

```
{"answer":"今天晚上吃青椒肉丝盖饭!","source":"fallback-fixed", ...}
```

后果：

1. `README.md:130`「默认无需任何 API Key，可使用本地规则讲解」、`README.md:146`「若云端调用失败，系统会自动降级回本地规则模式」、`README.md:158`「兜底：云端失败时自动回退本地规则」——**全部与代码不符**。
2. `buildLocalAssistantAnswer()`（`src/server.js:340`）和 `findMatchedPresetQa()`（`src/server.js:367`）**写完从未被调用**，是死代码；`place.ejs:261-267` 的 `sourceLabelMap` 里预留的 `preset` / `local` 两个标签永远不会出现。
3. 现在只要云端报错（Key 失效、超时、限流），用户在任何地点问任何问题，得到的都是"今天晚上吃青椒肉丝盖饭!"——这是**线上正在发生的事**（见 P0-2）。

```js
const preset = findMatchedPresetQa(place, question);
if (preset) {
  return res.json({ answer: preset.answer, source: "preset", ... });
}
return res.json({
  answer: buildLocalAssistantAnswer(place, question),
  source: "local",
  model: "local-rules",
  fallbackReason: cloudAttempt.fallbackReason,
});
```

### P0-3 首次登录强制改密可以被绕过

`requireAuth`（`src/server.js:174-182`）只看 `req.session.user` 是否存在，**从不检查 `mustChangePassword`**。全项目只有登录处（`549-551`）在跳 `/profile/password`。

**实测**：用首次登录账号 `20230003`/`20230003` 登录 → 302 到 `/profile/password`，但紧接着

```
GET /            -> 200   （页面正常渲染"欢迎你，20230003"）
GET /place/x-1   -> 200
```

即：直接敲网址就能跳过改密，`mustChangePassword` 只是个软提醒。61 个账号的初始密码等于学号，等于**任何知道同学学号的人都能免改密使用**。

**修法**：加一个中间件，挂在地图/详情/AI 接口前：

```js
function requirePasswordChanged(req, res, next) {
  if (req.session.user?.mustChangePassword) return res.redirect("/profile/password");
  next();
}
```

### P1-1 `change-password.ejs` 的 `<script>` 在 `</html>` 之后

`src/views/change-password.ejs:36-43`：脚本块位于 `</html>` 闭合标签**之外**。浏览器容错所以目前能跑，但这是无效 HTML，某些解析路径下会不执行。把 `</html>` 挪到最后一行即可。

### P1-2 详情页正文的换行全部丢失

`data/places.json` 里 `content` 用 `\r\n` 分段（如 `冶金学院` 有 2 段、`一二九公园` 有多段），但：

- `place.ejs:33` 用 `<%= place.content %>`（转义输出，不会生成 `<br>`）
- `public/styles.css:1129-1132` 的 `.content` **没有** `white-space: pre-wrap`

结果所有段落挤成一大坨。**修法**：给 `.content` 加 `white-space: pre-wrap;`（改动最小，且天然防止 HTML 注入）。CSS 里 `.assistant-bubble`（`1232`、`1358`）已有这个属性，可以照抄。

### P1-3 畸形 JSON 请求体会把服务器绝对路径吐给客户端

只要 `Content-Type: application/json` 的请求体不是合法 JSON，body-parser 抛错 → Express 默认错误处理器在非 production 环境返回**带完整堆栈的 HTML**：

```
SyntaxError: Unexpected token '}', "}{broken" is not valid JSON
    at createStrictSyntaxError (C:\Users\25043\Desktop\xiaoshiditu\node_modules\body-parser\...)
    at parse (...raw-body/index.js:238:16)
```

本机 `NODE_ENV` 未设置，线上若也没设就是同样的输出。**修法**：在 `996` 行前加

```js
app.use((err, req, res, next) => {
  if (err && err.type === "entity.parse.failed") {
    return res.status(400).json({ error: "请求体不是合法 JSON" });
  }
  console.error(err);
  return res.status(500).json({ error: "服务器内部错误" });
});
```

（这是**唯一**一处向客户端泄露路径的地方；我检查过 `image/delete` 的 `fs` 操作和 `not-found` 渲染，都没有泄露。）

### P1-4 上传只校验客户端声明的 MIME，没校验文件内容

`src/server.js:43-50` 的 `fileFilter` 只判断 `file.mimetype.startsWith("image/")`，而 mimetype 是**请求头里客户端自己写的**。

**实测**：把一个 19 字节纯文本用 `filename=fake.jpg; type=image/jpeg` 上传 → **302 保存成功**，`public/uploads/1791711534553-621262828.jpg` 落盘，`places.json` 记录了它。如果同一个文件用 `type=text/plain` 上传 → 400 被正确拒绝。

后果：`public/uploads/` 里可以塞任意扩展名的任意内容（含 .html/.svg），并且它是**静态目录**（`server.js:162`）。**修法**：检查文件头魔数（`ffd8ff` / `89504e47` / `47494638` / `52494646`+`WEBP`），或改用 `sharp` 重新编码。

### P2-2 仓库里跟踪了不该跟踪的调试残留

| 文件 | 内容 | 判断 |
| --- | --- | --- |
| `cookie.txt` | Netscape 格式 cookie jar，含一条 `connect.sid=s%3AAni0noH4dzwP6NiNfb7xXbCflWdZY4iU…`（127.0.0.1，已过期） | **已跟踪**，应删除 |

`cookie.txt` 那条 session id 指向本机且时间戳已过期，风险有限；但**如果这条 cookie 曾经来自线上、而线上 `SESSION_SECRET` 又没设**（见 P2-4），历史上就存在会话可被复用的窗口。建议顺手在服务器上把 `SESSION_SECRET` 设成一个固定随机值（这会一次性让所有旧会话失效）。

### P2-3 密码修改流程是"改完踢下线"而不是"改完继续用"

`src/server.js:676-683` 在改密成功后立刻 `req.session.destroy()`，然后 `change-password.ejs:38` 弹一个 `alert("改动成功")`，800 ms 后跳 `/login`。用户被强制重新登录一次。功能上说得通，但体验偏硬；若想顺滑，可改为保留会话并刷新 `mustChangePassword`。

### P2-4 `SESSION_SECRET` 未设置时，每次重启都会把所有人踢下线

`src/server.js:154`：

```js
secret: process.env.SESSION_SECRET || require("crypto").randomBytes(32).toString("hex"),
```

兜底是**每次进程启动随机生成**。交接文档 `docs/新电脑开发交接文档.md:75` 已把"重启服务会清空登录状态"写成正常现象——但它不该是常态。线上应在 pm2 环境里固定注入 `SESSION_SECRET`。

### P2-5 后台写坏了 `admin_ids.json` 会静默失去管理员权限

我体检时用 PowerShell 5.1 的 `Set-Content -Encoding UTF8` 写 `admin_ids.json`，结果写入 UTF-8 **BOM**（`EF BB BF`）。`userStore.readJson` 的 `JSON.parse` 抛错 → 静默回退到默认值 `["20230001"]` → 账号 `1`、`2` 的管理员标志全部消失，`/admin` 一律 403，**且没有任何日志**。

`README.md` 末尾已经提醒过"PowerShell 带中文要存 UTF-8 带 BOM"，但结论正好相反：**这里必须是无 BOM**。建议：

1. `README.md` 补一句"`data/*.json` 必须存为 **UTF-8 无 BOM**"；
2. `readJson` 里 `raw.replace(/^\uFEFF/, "")` 兜一下，把静默失败变成可恢复。

### P2-6 任何一次后台保存都会重写整个 `places.json`，历史 `\r\n` 换行被抹平

`placeStore.writePlaces`（`src/services/placeStore.js:24-26`）把**整个数组**重新 `JSON.stringify` 写回，`addPlace`/`updatePlace`/`deletePlace` 都走它。原始文件里 `content` 用的是 Windows 的 `\r\n`（如「冶金学院」两段之间），而 `JSON.stringify` 输出的是 `\n`。

**体检中已实际发生**：我通过 `image/delete` 触发了一次 `updatePlace`，`data/places.json` 的 mtime 随之变化，全文换行被统一成 `\n`（这也是报告里唯一被改动的源数据文件）。功能无影响，但会制造"只改了一个地点却整文件 diff"的噪音，也让 `scripts/update-server.sh:108-119` 的地点对比更难读。若在意，可在 `JSON.stringify` 后 `.replace(/\n/g, "\r\n")`，或把数据文件的换行风格 `git config core.autocrlf` 固定下来。

### P3-4 安全加固（校园项目可接受，但值得知道）
